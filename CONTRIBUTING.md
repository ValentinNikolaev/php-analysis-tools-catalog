# Contributing

Thank you for helping improve the PHP analysis tools catalog. Contributions can
correct catalog metadata, propose tools, improve the generated site, or improve
the maintenance scripts and tests.

By participating, you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).
Catalog inclusion, lifecycle, recommendation, provenance, and conflict-of-interest
rules are documented in [EDITORIAL-POLICY.md](EDITORIAL-POLICY.md).
Unless a contribution explicitly states otherwise and is accepted on different
terms, code contributions are provided under MIT and catalog/editorial
contributions under CC BY 4.0, matching the repository licenses.

## Before You Start

- Search existing issues and pull requests before opening a duplicate.
- Use an issue form for a catalog correction or a new tool proposal when you are
  unsure whether a pull request is appropriate.
- Keep each pull request focused on one logical change.

## Development Setup

The project uses Python 3.12 and the Python standard library. No dependency
installation is required.

Run the test suite from the repository root:

```shell
python -m unittest discover -s tests
```

Build the site locally into a disposable directory:

```shell
python scripts/generate_site.py --output site-dist
```

For the static category/tool routes, selection-guide sources, sitemap, and
account-side search-engine setup, see [Search indexing](docs/search-indexing.md).

## Catalog Changes

`common/catalog/*.yaml` is the source of truth for published catalog entries.
`common/candidates/*.yaml` contains discoveries that still need editorial
review. Do not edit generated catalog tables in `README.md`,
`EDITORS-CHOICE.md`, the legacy `EDITOR-CHOISE.md` compatibility file, or
`site/` as a substitute for changing the source data.

When adding or updating an entry:

1. Use a lowercase, hyphenated filename matching the entry's `slug`.
2. Use one of the stable categories defined in `scripts/catalog_lib.py`, then
   add the independent `artifact_type`, `use_cases`, and `ecosystems` fields.
3. Provide the official project and repository URLs when available.
4. Keep descriptions factual and concise; avoid promotional claims.
5. Do not add an `editor_choice` field to an entry. Editors' Choice membership
   is maintained only in `common/editor-choice.yaml` and requires human review.
6. Add a short pro, con, and official source URL to `common/pros-cons.yaml`.
   These summaries are editorial copy: update them manually and do not derive
   or overwrite them during metadata refreshes.
7. Set `reviewed_at` to the date on which the editorial fields and primary
   sources were checked. Do not use a metadata refresh timestamp as a review.
8. Validate and regenerate the derived files:

   ```shell
   python scripts/validate_catalog.py
   python scripts/generate_editor_choice.py
   python scripts/generate_readme.py
   python scripts/generate_exports.py
   python scripts/generate_site.py --output site-dist
   ```

The full metadata refresh contacts GitHub, Packagist, and project websites. Run
it only when the contribution needs current external metadata:

```shell
python scripts/full_workflow.py --skip-discovery
```

## Candidate Review

Discovery writes review records only; it never promotes a repository directly
into the public catalog. Every candidate must have a `review_status`, review
notes, discovery date, and last-review date. Rejected candidates are kept in
`common/rejected-candidates.yaml` so repeated searches do not recreate known
false positives without new evidence.

A candidate is promoted by a focused pull request that adds a complete catalog
record, editorial pro/con/source material, and passes the validator. Popularity
alone is not an inclusion criterion.

## Code and Workflow Changes

- Add or update tests for behavior changes.
- Preserve the deterministic generated output.
- Use `--as-of` or `SOURCE_DATE_EPOCH` when a reproducible lifecycle snapshot
  is required.
- Keep `.codex/` as the source of truth for agent configuration; `.claude/` is
  generated by automation.
- Never commit tokens, credentials, private vulnerability details, or generated
  `site-dist/` output.

## Pull Request Checklist

Before submitting a pull request:

```shell
python -m unittest discover -s tests
git diff --check
git status --short
```

Explain what changed, why it changed, and which verification commands you ran.
